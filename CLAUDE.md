```bash

flutter run

# Static analysis
flutter analyze

# Tests
flutter test                              # all tests
flutter test test/path/to/file_test.dart  # single file

# Code generation (injectable DI). Required after adding/removing
# @injectable / @lazySingleton / @LazySingleton(as: ...) annotations.
dart run build_runner build --delete-conflicting-outputs
dart run build_runner watch --delete-conflicting-outputs   # continuous
```

**Never hand-edit `lib/core/di/injection.config.dart`** — it is generated by `build_runner`. Hand-edits get silently overwritten on the next codegen run.

## Architecture

### Clean Architecture per feature

Every feature under `lib/features/<name>/` is split into three layers with a strict dependency direction `presentation → domain → data` (domain has no Flutter or package dependencies beyond `dartz` and `equatable`):

```
features/<name>/
├── domain/         entities, abstract repository, use cases, failures
├── data/           models (with fromJson/toEntity), datasources, repository impl, exceptions
└── presentation/   bloc/, pages/, widgets/, utils/ (error mapper)
```

Repository interfaces live in `domain/`, implementations in `data/`. Use cases implement `core/usecases/usecase.dart`'s `UseCase<Type, Params>` and return `Future<Either<Failure, Type>>` (dartz). Blocs depend on use cases, never on repositories directly.

### Error flow

A single uniform pipeline carries errors from network/SDK to UI:

1. **Data layer throws custom exceptions** from `core/error/base_exceptions.dart` (`ServerException`, `NetworkException`, `UnauthenticatedException`, `ConflictException`, `ApiException`) or feature-specific ones in `data/exceptions/`. **External package exceptions (e.g. supabase's `AuthException`, dio's `DioException`) must be caught inside the data layer and re-thrown as one of these custom exceptions** — they must not leak to the repository.
2. **Repository impl maps exceptions to `Failure`** (`core/error/base_failures.dart` + feature-specific `domain/failures/`) and returns `Left(failure)` / `Right(entity)`.
3. **Bloc folds the `Either`** and emits an error state whose message comes from a `<Feature>ErrorMapper` in `presentation/utils/`. Mappers fall through to `core/utils/core_error_mapper.dart` for generic failures.

`DioHttpClient` ([lib/core/network/dio_http_client.dart](lib/core/network/dio_http_client.dart)) is the single place that translates `DioException` → custom exceptions based on status code. All HTTP calls go through the `AbstractHTTP` interface, never raw `Dio`.

### Dependency injection (get_it + injectable)

`getIt` is configured in [lib/core/di/injection.dart](lib/core/di/injection.dart) and initialized in `main.dart` via `configureDependencies()`. Annotate registrations:

- `@lazySingleton` — most things (data sources, repos, use cases, http client)
- `@LazySingleton(as: SomeAbstract)` — when binding an impl to its interface
- `@injectable` (factory) — Blocs (so each page gets a fresh instance)
- `@module` — third-party deps that need manual construction (see `core/di/modules/`)

After changing annotations, regenerate `injection.config.dart` with `build_runner`.

### Routing & Bloc provisioning

`go_router` config lives in [lib/config/routes/app_router.dart](lib/config/routes/app_router.dart). **`BlocProvider` for a page is wired in the route's `builder`, not inside the page file.** Pattern:

```dart
GoRoute(
  path: '/profile',
  builder: (context, state) => BlocProvider<ProfileBloc>(
    create: (_) => getIt<ProfileBloc>()..add(FetchUserProfileData()),
    child: const ProfilePage(),
  ),
),
```

Pages are pure UI consumers (`BlocBuilder` / `BlocListener`). Sub-widgets (loading view, error view, data view, etc.) go in their own files under `presentation/widgets/`, **never as private classes inside the page file**.

### Authentication

Hybrid: **Supabase handles identity** (sessions, OAuth tokens, JWT issuance), **the custom Spring backend handles app data**. The Supabase JWT is the bearer token for backend calls.

- [`SupabaseAuthDataSource`](lib/features/authentication/data/datasources/supabase_auth_data_source.dart) — wraps Supabase + Google Sign-In, also reads from a `profiles` table to determine `requires_onboarding`.
- [`AuthApiDataSource`](lib/features/authentication/data/datasources/auth_api_data_source.dart) — calls the Spring backend.
- [`AuthInterceptor`](lib/core/network/auth_interceptor.dart) — dio interceptor that pulls `supabaseClient.auth.currentSession?.accessToken` and sets `Authorization: Bearer <jwt>` on every request.
- Session persistence uses [`SecureLocalStorage`](lib/core/storage/secure_local_storage.dart) (flutter_secure_storage) plugged into Supabase's `FlutterAuthClientOptions`.

### Backend contract

- Base URL: `${API_BASE_URL}/public/api/v1` (configured in [lib/core/di/modules/dio_module.dart](lib/core/di/modules/dio_module.dart); `API_BASE_URL` lives in `.env`, currently `http://localhost:8080`).
- All endpoints require the JWT. The interceptor handles this — call sites never set `Authorization` manually.
- JSON is **snake_case**. Models map snake_case JSON → camelCase Dart fields in `fromJson`.

## Conventions worth knowing

- All paths in `lib/` use **relative imports within the same feature** and `package:car_social_media_app/...` across features (existing code mixes both — match the surrounding file).
- Environment variables: read via `dotenv.env['KEY']` after `await dotenv.load(fileName: ".env")` in `main.dart`. `.env` is listed in `pubspec.yaml` assets.
- `analysis_options.yaml` uses `flutter_lints` defaults — no custom rules.
